# 项目决策记录

记录日期：2026-09-28。以下条目来自项目所有者在当前项目会话中的明确要求及仓库 Agent 指引；引文只保留影响决策的短句。运行是否成功、当前线上版本及 Git 发布状态须另查实际证据，不能由“已接受”推断。

## D-001：审查回复服务于合并判断

- 状态：已接受。
- 用户选择：“说明本次改了什么、检查结果，以及能否合并”。用户同时指出同一份回复出现两次、内容没有提供有用信息。
- 决策：PR 只维护一条持续更新的自动验收回复。优先呈现实际改动、检查结果、阻塞原因或合并建议；逐项证据与技术元数据折叠展示。PR 正文使用稳定的需求概述，合并后同步状态。
- 原因：用户需要据此作决定，重复的全文通知和日志路径不能代替审查结论。
- 范围：Symphony 自动验收产生的 PR；通过审查不代表获得自动合并权限。
- 正文：[审查回复与页面证据](SYMPHONY_ACCEPTANCE.md#审查回复与页面证据)。实例：[PR #22 的审查回复](https://github.com/dailiuyi/blog/pull/22#issuecomment-5862723913)。

## D-002：页面审查必须有实际浏览器证据

- 状态：已接受。
- 用户选择：“检查代码并实际打开页面，附截图和交互验证结果”；截图位置选择：“直接在 GitHub 审查回复中查看”。
- 决策：审查源码和准确候选版本的实际页面，保存截图与相关交互结果，把图片直接嵌入 PR 回复。只读源码不能宣称已打开页面；模型也需要查看实际截图。
- 原因：源码检查无法独立证明页面外观和交互达到需求。
- 实现选择：目前覆盖 1440、390、320px，使用隔离浏览器和候选提交的独立构建；截图发布至 `codex/acceptance-evidence`，链接固定证据提交。具体宽度和存储分支是实现方式，不是用户要求永远不变的产品约束。
- 正文：[审查回复与页面证据](SYMPHONY_ACCEPTANCE.md#审查回复与页面证据)。

## D-003：合格的标签事件自动完成登记和入队

- 状态：已接受。
- 用户要求：“用户只需要打上标签，然后就可以自动授权登记、注册和入队”。当前 AGENTS 指引明确授权 label-driven intake。
- 决策：允许账号先完成计划及模型/深度标签，最后添加 `symphony:ready`；监听器核验事件并自动登记授权、注册和入队，不再重复要求聊天确认。模型标签本身及历史 ready 标签不代表本次授权。
- 边界：选择 DeepSeek 并添加合格 ready 事件，授权仅限该 Issue 的提示和必要工作区内容发送至指定提供商；变更计划或路线需要新的授权事件。自动化不扩大合并或部署权限。
- 正文：[入队和人工操作](SYMPHONY_ACCEPTANCE.md#入队和人工操作)、[WORKFLOW.md](../WORKFLOW.md)。

## D-004：自动验收、人工确认和线上验收分别记录

- 状态：已接受，来源为项目所有者提供的 AGENTS 指引及本次验收讨论。
- 决策：预合并源码与浏览器证据绑定候选 SHA；人工验收保存实际确认来源；线上验收必须在获准部署后绑定实际线上版本。预合并计划不能要求尚未发生的生产部署结果。
- 原因：避免出现“必须先上线才能允许合并”的循环，也避免用户已确认后仍无条件显示“待人工验收”。
- 边界：对 PR #20 的合并和部署授权仅适用于那次操作，不能推导成后续 PR 的自动发布权限；合并行为本身也不能替代页面或线上验收。
- 正文：[证据与交付](SYMPHONY_ACCEPTANCE.md#证据与交付)。

## D-005：把项目决定写回项目文档

- 状态：已接受；本次用户反馈：“为什么不将我的决策和项目有关的文档留存起来”。
- 决策：主机操作者在同一任务内记录持久决策及理由、更新相关规格或运维正文，并提供下一次任务的读取入口。收尾时说明保存、提交、发布及安装状态，不能把本机已生效等同于项目文档已交付。
- 原因：只留在聊天、PR 评论、忽略目录或未说明位置的工作树里，会让下一次任务重新询问或读取旧规则。
- 边界：不归档完整聊天或凭据；记录项目知识不等于修改用户全局记忆，也不等于获准发布。受限的编码和审查 agent 继续遵守各自的修改范围，由主机操作者处理跨任务文档。
- 正文：[项目文档入口](README.md)、[AGENTS.md](../AGENTS.md)。

## D-008：审查意见自动进入修复和复验循环

- 状态：已接受。2026-09-28 用户要求：“既然提出了反对意见，我希望编码 agent 能直接接收到这个反对意见然后改，形成一个循环”。
- 决策：有证据的代码缺陷和未实现需求，将完整审查意见及修复要求自动交给编码 agent；修改后重新执行检查和独立审查。上一轮反馈在同计划重新入队及人工恢复时继续保留。
- 原因：用户不应反复搬运审查意见，自动验收拒绝后应由具备权限的执行方继续处理。
- 实现边界：PR #24 的实际阻塞是页尾及 Night 截图缺失，源码及三项检查已通过。新增 `recapture` 结论，由控制器按意见重新生成浏览器计划、补拍并复验同一候选 SHA；截图问题不要求编码 agent 越权或制造无关代码提交。源码返工与证据补充共用最多三次自动修复额度，真实环境/权限问题及需要用户澄清的需求仍阻塞。
- 授权范围：沿用 Issue 已登记的计划、路径、模型路线和提供商授权；自动反馈不授予合并、部署或任意 PR 评论派发权限。
- 来源：[PR #24 审查意见](https://github.com/dailiuyi/blog/pull/24#issuecomment-5863614949)及本次用户要求；正文：[自动反馈与复验循环](SYMPHONY_ACCEPTANCE.md#自动反馈与复验循环)。
